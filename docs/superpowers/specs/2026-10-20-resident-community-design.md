# 가입·차량 OCR·입주민 커뮤니티 변경 설계

날짜: 2026-10-20 (Asia/Seoul). 상태: 사용자가 화면 방향과 앱·별도 서버 로컬 코드 수정을 승인함. 로컬 구현·자동 검증 완료, 실기기 실행 및 운영 반영 미수행. 결과는 `docs/verification/RESIDENT_COMMUNITY_2026-10-20.md`를 참고한다.

## 요청과 범위

1. 전화번호 입력·전송·필수 검증·회원 화면 표시를 제거한다. QR 자동 주차와 직접 주차의 연락처 필수조건도 제거한다. 기존 서버 데이터 삭제는 관리자 명시적 실행으로만 수행한다.
2. 사용자 지시에 따라 닉네임을 필수로 수집한다(공백 제외 1~30자). Google 이름과 이메일은 읽기 전용 계정 정보로 유지하고 서비스에는 닉네임을 우선 표시한다. Google 로그인 기반 사용자 식별은 유지한다.
3. 차량번호 입력과 번호판 사진 OCR 비교를 제공한다. 입력값 전체는 번호판 하나에만 일치해야 한다. 두 번호를 쉼표·공백·줄바꿈·슬래시 등으로 입력하면 앱과 서버 모두 저장을 거절한다. 차량은 계정의 단일 필드이며 번호 변경은 기존 차량을 교체하고 새 OCR·관리자 재승인을 요구한다. 동일 번호에서 닉네임만 바꾸면 승인을 유지한다. 차량번호는 주차 서비스에 필요한 별도 데이터임을 안내한다. 사진을 사용하는데도 개인정보를 Google 정보만 수집한다고 안내하지 않는다.
4. 가입 흐름은 Google 로그인 → 수집 항목 안내/동의 → 차량번호 입력 및 사진 OCR 비교 → 관리자 승인 대기 → 최종 승인 후 회원 서비스다. 거절·차단·탈퇴 상태는 가입 보완보다 먼저 차단한다.
5. 관리자가 기존 개인정보 정리와 회원 전체 삭제를 구분해서 실행한다. 개인정보 정리는 전화번호·남은 인증 사진을 정리하고 Google 계정·차량번호·이용 이력을 유지한다. 필수로 수집한 닉네임은 보존한다. 회원 전체 삭제는 기존 회원 정리 기능을 재사용한다. 대상·삭제 범위를 확인하고 서버 응답 후 목록을 갱신한다.
6. 관리자 OCR 테스트는 비교할 차량번호와 사진을 입력받아 인식 후보·일치/불일치/인식 실패를 표시한다. 테스트는 회원 승인이나 데이터 저장을 수행하지 않는다.
7. 아파트 이슈 게시판은 승인 회원의 목록·상세·작성·본인 수정/삭제, 관리자의 게시물 삭제를 제공한다. 제목·본문과 작성 시각을 표시한다. 댓글·익명 글·추가 알림은 이번 범위에 포함하지 않는다.
8. 고장 신고는 승인 회원이 충전기/주차 위치·내용·선택 사진 1장을 제출한다. 신고자는 본인 신고 상태를 조회하고 관리자는 전체 신고와 접수/처리 중/완료 상태를 관리한다. 신고만으로 충전기를 자동 차단하지 않는다.

## 화면 방향

기존 Material 테마, Card/ListTile, Navigator/MaterialPageRoute를 유지한다. 하단 5개 탭은 유지하고 더보기 메뉴에 게시판과 고장 신고를 추가한다. 관리자 허브에는 OCR 테스트·신고 관리·개인정보 정리 진입점을 추가한다. 화면 초안은 `2026-10-20-resident-community-wireframe.svg`에 있다.

가입 화면은 Google 계정을 읽기 전용으로 표시하고 닉네임 필수 입력, 차량번호 입력, 카메라/갤러리, 사진 미리보기, 인식 후보와 비교 결과, 승인 요청 버튼 순서다. 번호 또는 사진을 바꾸면 이전 일치 결과를 즉시 무효화한다. 일치하지 않거나 OCR이 실패하면 제출하지 않고 재촬영을 안내한다. 승인 대기 화면에는 새로고침과 로그아웃을 둔다.

게시판은 목록/상세와 작성 폼을 나눈다. 고장 신고는 목록/상세와 제출 폼을 나누며 사진은 선택 사항이다. 로딩·빈 목록·오류·재시도를 제공하고 중복 제출을 막는다. 실패 시 입력을 보존한다. 접근 권한과 작성자 권한은 서버에서도 검사한다.

## 구현 선택 비교

- 권장: 휴대폰 한국어 OCR + 서버에 비교 결과와 차량번호 등록 + 관리자 최종 승인. 외부 OCR 서비스 계정 없이 동작하며 관리자 테스트도 같은 인식기를 재사용한다. OCR 결과는 소유권/입주민 신분 증명이 아니며 서버가 최종 승인 권한을 관리한다. 관리자 검토용 사진 보관 여부는 기존 계약과 함께 확정하고 보관 시 승인/거절 후 삭제한다.
- 대안: 서버 OCR. 중앙 검증과 웹 관리자 재사용에 유리하지만 서비스 설정·자격 증명·사진 전송 및 보관 정책이 추가로 필요하다.
- 기존 수동 사진 검토만 유지하는 방법은 OCR 요청을 충족하지 않아 채택하지 않는다.

새 OCR 패키지와 한국어 네이티브 모델은 공식 지원 조건·라이선스·Android/iOS 최소 버전을 확인한 후 버전을 고정한다. 기존 image_picker를 재사용하고 사진 전체 라이브러리 권한은 추가하지 않는다. 외부 OCR 서비스나 새로운 자격 증명을 만들지 않는다.

관련 서버는 `D:/vsCodeProg/APT-Prj`에 있으며 현재 `api/profile.js`가 전화번호/닉네임을 필수 검사한다. 모바일 코드만 바꾸면 가입 실패가 발생한다. `api/users.js`의 현재 회원 승인과 차량 승인 분리도 새로운 순서에 맞춰 서버에서 검사해야 한다. 게시판·신고·개인정보 정리 API는 실제 지원을 확인하고 서버와 앱을 함께 맞춘다. 서버 저장소 수정은 작업 범위 확인 후 진행한다. 운영 DB 정리·마이그레이션 실행·배포·게시·실제 회원 삭제는 이 설계 확인만으로 실행하지 않는다.

## 검증과 수락 기준

전화번호 없이 가입/직접 주차/QR 주차가 가능하고 요청에 전화번호가 포함되지 않아야 한다. OCR 번호 공백/하이픈 정규화, 한글 보존, 미인식/복수 후보/불일치, 입력 변경 후 결과 무효화를 검사한다. 일치만으로 승인 상태가 되지 않아야 하며 미완료 회원을 관리자가 우회 승인하지 못해야 한다. 거절/차단 계정과 계정 전환 후 늦게 도착한 응답도 검사한다.

게시물 작성자/관리자 권한과 신고자별 조회 범위, 관리자 상태 변경, 사진 크기/형식 실패, 중복 제출, 통신 실패 후 입력 보존을 검사한다. 삭제 실패 시 성공 메시지나 목록 선삭제가 없어야 한다.

Flutter SDK는 `C:/src/flutter`를 확인했다. `flutter analyze --no-fatal-infos`와 관련 테스트를 먼저 실행하고 변경 후 전체 회귀 테스트를 실행한다. 기본 API 주소는 운영이므로 테스트는 격리된 adapter/fixture로 수행한다. Android/iOS의 카메라·갤러리·한글 OCR·로그인·QR 흐름은 실기기에서 별도 확인하며 Windows에서 iOS 실행을 검증했다고 보고하지 않는다. Mermaid/JSON 색인은 실제 구현과 검증 뒤 함께 갱신한다.

## 작업 운영

사용자가 PM의 기존 설치 스킬 선택을 승인해 `cfg/blue-ocean.preferences.json`에 저장했다. Blue Ocean upstream HEAD/설치 기준은 `e0f597af83f59a83e769d8836b3960184c04e40a`로 동일하다. PM은 현재 세션이며 모델 정보는 검증되지 않았다. 설계 보조 에이전트는 gpt-6.1-sol이다. 가용 물리 메모리가 약 0.5GB이므로 설계 보조 1개만 사용하고 Flutter/서버 검증을 동시에 실행하지 않는다. 설계 보조가 시스템/GUI/QC 역할을 함께 맡아 이번 아이디어 검토는 역할별 독립 에이전트 검토가 아니다.

보조 스킬은 project-diagram(변경 영향 및 색인), brainstorming(설계 확인), writing-plans(구현 순서), test-driven-development(핵심 행동 검증), verification-before-completion(검증 증거)에 한정한다. 기존 사용자 변경을 보존하며 자동 커밋·대량 파일 이동을 수행하지 않는다.
