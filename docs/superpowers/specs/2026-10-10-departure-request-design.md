# 출차 요청과 차주 휴대폰 알림 설계안

상태: 사용자 승인에 따라 앱·서버 코드와 오프라인 검증 완료. Firebase 프로젝트 미확인. 운영 DB 적용·배포·실기기 검증 미수행. 최종 결과는 docs/verification/DEPARTURE_REQUESTS.md 참고.

서버 저장소: `D:/vsCodeProg/APT-Prj`. Vercel의 CommonJS Node.js 22 API와 Neon PostgreSQL을 사용한다. `package.json`, `api/state.js`, `api/chat.js`, `api/_lib/auth.js`, `api/_lib/db.js`, `api/_lib/messaging.js`를 확인했다. 기존 messaging은 관리자 가입 알림 이메일 전용이며 FCM 의존성이나 설정은 소스에서 발견되지 않았다. 운영 환경 변수의 값은 읽지 않았다.

## 목적

충전기 실시간 연동 없이 이용자가 현장에서 충전 완료를 확인한 경우, 사용 중인 차량 차주에게 출차를 요청한다. 예상 충전 시간이 남아 있어도 요청할 수 있다. 요청은 충전 완료 판정이나 자동 출차 처리가 아니다.

## 설계 당시 구현 근거

- `lib/widgets/slot_dialog.dart`: 타인 소유 슬롯은 조회만 가능하며 출차 요청 액션이 없다.
- `lib/screens/public/parking_list_screen.dart`, `map_view_screen.dart`: 공통 슬롯 상세를 사용한다.
- `lib/services/state_api.dart`: 주차 상태 조회/저장만 제공한다.
- `lib/services/chat_api.dart`: 수신자 없는 전체 채팅이다. 특정 차주 알림 대용으로 사용하지 않는다.
- `pubspec.yaml`: Firebase 및 휴대폰 알림 플러그인이 없다.
- 서버 구현은 이 저장소에 없다. 새 API를 운영 서버에서 이미 지원한다고 가정하지 않는다.

## 접근 방식 비교

1. **권장: 서버에 출차 요청 저장 + 개별 차주 푸시 + 앱 알림 목록.** 앱이 화면에 열려 있지 않아도 알림을 받을 수 있고 요청 이력을 다시 확인할 수 있다. 서버와 Firebase 설정이 필요하다.
2. 앱 실행 중 서버 조회로 요청 표시. 구현 부담은 적지만 앱이 닫혀 있을 때 휴대폰 알림 요구를 충족하지 못한다.
3. 전체 채팅에 요청 메시지 게시. 기존 API를 활용하지만 특정 차주에게 전달되는 것을 보장하지 못하고 다른 회원에게 불필요하게 공개된다.

## 화면과 동작

1. 승인된 회원이 다른 회원의 사용 중인 슬롯 상세를 열면 ‘출차 요청하기’를 표시한다. 본인 차량, 빈 슬롯, 차주 계정이 없는 차량에는 요청을 허용하지 않는다.
2. 확인 화면에 ‘충전 완료를 직접 확인하셨나요? 앱의 예상 시간은 실제 충전 상태와 다를 수 있습니다.’를 표시하고 요청 차량번호를 보여준다. 확인 후 전송한다.
3. 요청 차량은 로그인 회원의 등록 차량을 서버가 확인한다. 클라이언트가 임의의 요청자나 수신자를 지정할 수 없게 한다.
4. 알림 예시: ‘출차 요청 · 123가4567 차량에서 B1 급속 1번의 차량 이동을 요청했습니다.’ 요청 차량번호 공개 범위는 이 요청을 받은 차주로 한정한다.
5. 알림을 누르면 인증 확인 후 해당 요청 상세로 이동한다. 앱 내 알림 목록에서도 요청 차량, 주차 위치, 요청 시간을 확인한다. 확인했다고 표시하는 동작과 실제 출차 동작을 구분한다.
6. 요청만으로 슬롯을 비우지 않는다. 차주가 기존 출차하기를 통해 직접 출차한다.
7. 권장 재요청 제한은 동일 요청자·동일 주차 건에 5분이다. 서버에서 중복 전송과 빈번한 요청을 제한하고 앱은 서버의 재요청 가능 시간을 표시한다.
8. 전송 실패 시 재시도를 제공한다. 서버 요청 접수와 실제 알림 수신을 구분하고, 접수만으로 ‘상대방이 확인했습니다’라고 표시하지 않는다.

## 서버와 푸시 연동

- 기존 Vercel 서버를 유지하며 Neon에 출차 요청과 계정별 기기 토큰을 저장한다. Firebase는 휴대폰 푸시 전달에 사용하고 기존 서버·데이터베이스를 대체하지 않는다.
- 제안 계약: `/api/departure-requests`의 POST는 `slotId`, 화면에서 확인한 ??? `expectedOwnerEmail`, ?? `expectedStartTime`을 받되 실제 송신자·차량·수신자는 서버가 결정한다. GET은 현재 세션의 수신 요청만 페이지 단위로 반환하고 PATCH는 수신자에게만 읽음 처리를 허용한다. `/api/push-tokens`는 현재 세션의 기기 토큰 등록 및 해제를 제공한다. 구체적인 응답 모델과 동시성 처리 계약은 구현 계획에 명시한다.
- 기존 `requireApprovedSession`, `requireSafeOrigin`, 공용 JSON 응답과 오류 처리 방식을 재사용한다. 중복 요청 제한은 Vercel 프로세스 메모리에 의존하지 않고 Neon에서 원자적으로 처리한다. 주차 건 검증은 캐시된 상태만으로 판단하지 않는다.
- Vercel 함수가 종료된 뒤 사라질 수 있는 미대기 Promise로 푸시를 보내지 않는다. 요청 저장 후 발송 결과를 기록하며 실패 시에도 요청 목록은 유지한다.
- 서버는 세션, 승인 상태, 요청자 등록 차량, 현재 슬롯 차주와 주차 건을 검증한 뒤 요청을 저장한다. 화면을 연 뒤 차주가 바뀌었거나 이미 출차한 경우 기존 차주에게 보내지 않는다.
- 요청 생성·수신 목록·읽음 처리 및 기기 토큰 등록/해제 API를 실제 서버 구조에 맞게 정의한다. 현재 단계에서는 미확인 엔드포인트를 앱에 추가하지 않는다.
- 로그인 계정과 기기 토큰을 연결하고 토큰 갱신·로그아웃·계정 전환 때 정리한다. 알림 상세 접근은 서버가 수신자 권한을 검사한다.
- Firebase Cloud Messaging으로 해당 차주의 기기에 알림을 보낸다. 발송 자격증명은 서버에만 둔다. Android 알림 권한과 채널을 설정하며 iOS 지원에는 APNs와 네이티브 설정이 추가로 필요하다.
- 알림 권한 거절이나 푸시 전달 실패가 있어도 요청은 앱 내 목록에 남긴다. 앱 실행 중에도 요청을 확인할 수 있다.
- 강제 중지, 네트워크 단절, OS 알림 제한에 따른 전달 한계는 실제 기기 검증에서 구분한다.

## 구현 범위와 검증

주요 영향 구성요소는 member-ui → services → http → backend, app/auth → 기기 토큰 수명, platform → 알림 수신과 진입이다. 구현 후 Mermaid와 JSON 색인을 함께 갱신한다.

클라이언트 및 서버 테스트는 요청 가능 조건, 본인/비회원 요청 차단, 차량 식별, 수신자 권한, 차주 변경, 중복 요청, 실패 처리, 로그아웃·계정 전환, 알림 진입을 검증한다. Flutter 정적 분석과 관련 테스트를 수행하고 두 개의 실제 계정·휴대폰에서 전경/백그라운드/종료 상태 알림과 요청 차량 표시를 확인한다. 운영 차주에게 테스트 알림을 보내지 않고 확인된 테스트 환경을 사용한다.

## 승인 및 남은 운영 작업

- 사용자 작업 진행 승인에 따라 앱·서버 코드와 구조도를 작성했다.
- APT 서버 저장소 경로는 확인했다. 사용 중인 Firebase 프로젝트는 확인이 필요하다. 미사용이면 새 프로젝트 설정 경로를 정한다.
- 서버 계약은 구현했다. Firebase 설정·운영 DB 적용·실기기 검증 후 배포해야 휴대폰 간 알림을 사용할 수 있다.

구현 계약 보완: 기존 상태 API는 타인 이메일을 숨긴다. 선택적 expectedOwnerEmail 없이도 슬롯과 원본 입차 시각으로 서버가 현재 주차 건을 검증한다. 요청 ID는 십진수 문자열이며 GET은 수신자 전용 ID 조회도 지원한다. 새 API는 APT-Prj에 구현했으며 운영 서버에는 아직 적용하지 않았다.
